# pseudo-jepa, v2
<!-- id: v2 · chapter: Overview · scene: v2-overview · map: all -->

> **Planned, not trained.** This is the version I'm building next. The animations reuse v1's photo and caption to show the plumbing; no number on this tab comes from a trained v2.

v1 learns by elimination: out of 256 captions, pick the right one. v2 learns by **filling in blanks**. Hide part of the photo, hide some words, and ask the network to predict what is missing. It never predicts pixels or words, only their 256-number representation. That is the JEPA idea: Joint-Embedding Predictive Architecture.

Three guessing games, all graded the same way.

## Hide part of the photo
<!-- id: mask · chapter: Image · scene: mask · map: image -->

On the $8 \times 8$ token grid, pick four rectangles, each about 15% of the grid. Those are the **targets**. The rest is the **context**, a bit under half the photo. The rectangles are large on purpose: hide one token and its neighbours give it away; hide a block and the network has to understand what is there.

## The context encoder
<!-- id: context · scene: context · map: image-blocks -->

v1's Image Encoder, unchanged: Convolution Stem, Positional Embeddings, six Transformer blocks. The difference is that the hidden tokens are dropped after the positional embeddings, so the blocks only ever see the context.

## The slow copy
<!-- id: ema · scene: ema · map: image-encoder -->

A second Image Encoder looks at the **whole** photo and provides the answers. It is never trained by the loss. After every step its weights move a tiny bit toward the context encoder's:

$$\bar\theta \leftarrow \tau\,\bar\theta + (1 - \tau)\,\theta, \qquad \tau: 0.996 \to 1$$

Because the answer key drifts slowly instead of chasing the guesses, the network cannot win by making everything equal. This is how JEPAs avoid collapse without wrong answers.

## Game 1: fill in the photo
<!-- id: game-image · scene: game-image · map: predictor -->

An image predictor (two Transformer blocks, like v1's) gets the context tokens plus one **mask token** per hidden position, carrying only that position's embedding. It outputs a guess for each hidden token, compared with the slow copy's token at the same spot:

$$\mathcal{L}_\text{image} = \text{SmoothL1}\big(\text{guess}, \ \text{slow copy}\big)$$

## Game 2: fill in the caption
<!-- id: game-text · chapter: Text · scene: game-text · map: text-blocks -->

The same game on words. Hide about 30% of a caption's words. The Text Encoder reads the rest, a text predictor guesses the hidden words' vectors, and a slow copy of the Text Encoder, reading the full caption, grades them. This gives the Text Encoder something to learn from on its own.

## Game 3: the bridge
<!-- id: game-bridge · chapter: Bridge · scene: game-bridge · map: target -->

v1's Predictor, with its accumulator q, reads the context tokens and predicts the slow text copy's **TARGET** for the full caption. The photo has holes and the answer comes from a slow copy, so it can't be matched by memorising. It is graded by angle:

$$\mathcal{L}_\text{bridge} = 1 - \cos(\hat y, \ \bar y)$$

## No wrong answers needed
<!-- id: total · chapter: Loss · scene: v2-loss · map: loss -->

$$\mathcal{L} = \mathcal{L}_\text{image} + \mathcal{L}_\text{text} + \mathcal{L}_\text{bridge}$$

There is no 256 × 256 table any more: every photo is graded on its own, so the batch size stops mattering. The risk moves elsewhere. If every vector drifts to the same point, the loss reaches zero and nothing is learned. I'll log the spread of the slow copy's vectors every epoch; if it falls toward zero, the run has collapsed.

## How it will be judged
<!-- id: plan · chapter: Next · scene: v2-plan · map: all -->

Same checkpoint rules, same 1,014 validation photos, same Results tab: score a photo against all 5,070 validation captions and count how often its own caption comes first. If v2 beats v1 while training on the same 29,000 photos, filling in blanks taught it more than elimination did.
